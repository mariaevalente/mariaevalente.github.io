Why one file

Controllers, training data and evaluation all need the same facts about a building: its zones and comfort ranges, its equipment and how the units depend on each other, its opening hours, and the map of sensors and commands. Without a shared description, each new building needed hand-written setup in several places. I made those facts a single declarative file that every tool reads. A new building, or a new kind of building, is now a new file.

Running it

The whole run is seven scripted steps: generate the scenarios, simulate them, train the models, report on them, and run the three controllers on the same year. It runs unattended on cloud VMs. I wrote the spec schema, its API layer and the sanity tests that every new building has to pass, and I generalised the controller so that it reads nothing but the spec.

Reproducibility

I designed and documented the team's experiment workflow. Calibration, data generation and training are separate stages, each tagged in Git. DVC versions the data and the models in cloud storage, and MLflow records every run with the exact inputs and commit IDs it used, so any result can be traced back to how it was made.
